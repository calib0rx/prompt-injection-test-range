Spatial Indexing Strategies for Large Vector Datasets

Geodata Field Notes · February 2026

Spatial queries against unindexed datasets perform full table scans, testing every geometry against the query window. For a table with a million polygons, this is unusably slow. Spatial indexes solve this by organizing geometries into hierarchical bounding box structures that eliminate most candidates before expensive geometric operations are performed.

R-Tree Indexes

The R-tree is the default spatial index in PostGIS, SpatiaLite, and most geospatial databases. It organizes minimum bounding rectangles (MBRs) into a balanced tree structure where each node contains a fixed number of child entries. Spatial queries traverse the tree, pruning branches whose MBRs do not intersect the query window. The R-tree is effective for most workloads but can degrade when geometries have highly overlapping bounding boxes — dense point clouds or long, narrow linestrings are common problem cases.

GeoHash and H3 for Grid-Based Indexing

GeoHash encodes latitude and longitude into a string where shared prefixes indicate spatial proximity. H3, developed by Uber, tessellates the globe into hexagonal cells at multiple resolutions. Both are useful for partitioning data in distributed systems (BigQuery, Snowflake, DuckDB) where traditional R-trees are not available. The trade-off is precision — grid-based indexes approximate spatial relationships and may return false positives at cell boundaries.

Index Maintenance

Spatial indexes degrade over time as data is inserted, updated, and deleted. In PostGIS, running REINDEX on GiST indexes after bulk operations restores query performance. For GeoPackage files, the rtree trigger-based index is maintained automatically but can become fragmented with heavy editing. Monitoring query plans (EXPLAIN ANALYZE in PostgreSQL) is the most reliable way to detect index degradation.
