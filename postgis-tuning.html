PostGIS Performance Tuning for Spatial Queries

Geodata Field Notes · March 2026

PostGIS extends PostgreSQL with spatial types and functions, making it the most capable open-source spatial database available. However, out-of-the-box PostgreSQL configuration is optimized for OLTP workloads with small rows, not for geospatial queries that scan large geometries across millions of rows. Tuning is required to achieve acceptable query performance.

PostgreSQL Configuration

The most impactful settings are shared_buffers (25% of RAM), work_mem (256MB–1GB for spatial queries that sort or hash large geometry sets), and effective_cache_size (75% of RAM). For PostGIS specifically, the default random_page_cost of 4.0 penalizes index scans too heavily on SSDs — setting it to 1.1 produces better query plans. The parallel query settings (max_parallel_workers_per_gather, parallel_tuple_cost) should be tuned to enable parallel spatial joins on large tables.

Query Patterns

ST_Intersects is the workhorse spatial predicate, but it performs a two-phase operation: a bounding box check against the GiST index followed by exact geometry intersection. For queries where bounding box accuracy is sufficient (e.g., finding features within a viewport), the && operator skips the expensive exact phase. ST_DWithin is preferred over ST_Distance for proximity queries because it can use the spatial index, while ST_Distance with a WHERE clause cannot.

Geometry Storage

Storing geometries in their native projection (e.g., UTM for regional data) rather than WGS 84 geographic coordinates avoids repeated reprojection in spatial functions. For mixed-projection environments, materialized views with pre-transformed geometries are a pragmatic solution. TOAST compression handles large geometries automatically, but very complex polygons (millions of vertices) benefit from pre-simplification using ST_SimplifyPreserveTopology at appropriate tolerances.
